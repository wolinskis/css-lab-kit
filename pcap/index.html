🎯 Goal: practise network forensics in Wireshark — one capture per level, each a different protocol, so the real skill is choosing the right display filter to pull the secret out of a busy capture. Recover the credential/flag at each level.

Four small captures, four protocols: cleartext HTTP, FTP buried in LAN noise, DNS exfiltration, and an encrypted SSH brute force. Everything is solved in the Wireshark GUI — the display-filter bar, Follow ▸ Stream and Statistics. Full answers in solution.md.

Files: http_login_cleartext.pcap · cases/case1_busy_lan_ftp.pcap · cases/case2_dns_exfil.pcap · cases/case3_ssh_bruteforce.pcap (open each with File ▸ Open; Statistics ▸ Protocol Hierarchy shows the protocol mix)

1 · Cleartext HTTP login 🟢 Easy

📥 http_login_cleartext.pcap

A user logs in to portal.vulncorp.local over plain HTTP. Recover the form username & password. Bonus (same capture): there is a second credential in a request header and a decodable session cookie in the response.

💡 Wireshark steps
  1. Display-filter bar: http — the capture shrinks to the request/response pair.
  2. Right-click the POST /login packet ▸ Follow ▸ HTTP Stream — read the form body at the bottom of the request.
  3. Bonus header: filter http.authorization; expand Hypertext Transfer Protocol in the packet details — the value after Basic is base64, decode it outside Wireshark (CyberChef, or echo '…' | base64 -d).
  4. Bonus cookie: filter http.set_cookie; the session= value is base64 JSON — decode it the same way and look at the role field.

http.authorization
http.set_cookie

2 · FTP login in a busy LAN 🟡 Medium

📥 cases/case1_busy_lan_ftp.pcap

About 81 frames of DNS, mDNS, NBNS, SSDP, ARP and HTTP chatter hide one plaintext login. Find the FTP server, the username and the password. Hint: http is a decoy here.

💡 Wireshark steps
  1. Statistics ▸ Protocol Hierarchy — spot the one small plaintext login protocol among the noise.
  2. Display-filter bar: ftp (or tcp.port==21) — only the control channel remains.
  3. Narrow to the login lines with ftp.request.command — the USER and PASS rows are the answer.
  4. Or right-click any FTP packet ▸ Follow ▸ TCP Stream to read the whole conversation (server greeting, USER, PASS, 230 Login successful).
ftp
tcp.port==21
ftp.request.command

3 · DNS exfiltration 🟠 Hard

📥 cases/case2_dns_exfil.pcap

About 51 DNS frames of ordinary browsing — and a few queries that are not browsing at all. Find the attacker domain, pull the data out of the subdomain labels and decode the flag.

💡 Wireshark steps
  1. Display-filter bar: dns, then scroll the Info column — most names are readable, a few are high-entropy gibberish under one domain. That is the tell-tale.
  2. Narrow to that domain: dns.qry.name contains "evil-exfil" — five queries remain.
  3. Write down the left-most label of each query name, in packet order, and join them into one string.
  4. Upper-case letters plus digits 2–7 = base32. Decode outside Wireshark (CyberChef "From Base32", or printf '…' | base32 -d).
dns
dns.qry.name contains "evil-exfil"

4 · SSH brute force 🔴 Expert

📥 cases/case3_ssh_bruteforce.pcap

SSH is encrypted, so you cannot read the password — analyse the pattern instead. Who is the attacker, how many attempts were made, and which connection is the one that succeeded?

💡 Wireshark steps
  1. Display-filter bar: tcp.port==22 && tcp.flags.syn==1 && tcp.flags.ack==0 — one row per connection attempt; count them and read the Source column.
  2. Statistics ▸ Conversations ▸ TCP tab — sort by Bytes. Almost every conversation is tiny (reset right after the version banner = failed auth); one is much bigger and ends with a clean FIN.
  3. Right-click that odd-one-out ▸ Follow ▸ TCP Stream (or filter on its client port) to confirm it carries a full session.
tcp.port==22 && tcp.flags.syn==1 && tcp.flags.ack==0
tcp.flags.reset==1 && tcp.port==22
