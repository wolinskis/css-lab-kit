🎯 Goal: decrypt a captured HTTPS session in Wireshark using the server's recovered RSA private key, read the login + flag — then meet a second capture where the same key fails (forward secrecy / ECDHE) and you must decrypt it with a TLS key log (SSLKEYLOGFILE) instead.

Scenario: an incident-response capture of a user reaching the internal portal portal.lab.local. The server's private key was later recovered from a backup. Everything is solved in the Wireshark GUI — open the pcap, set one TLS preference, Follow ▸ TLS Stream. Two parts, four levels. Full answers in solution.md (Part 1) and solution_pfs.md (Part 2).

Files: portal_tls.pcap · server.key · server.crt · portal_pfs.pcap · portal_pfs.keys (Part 1: first three · Part 2: last two + the same key/cert, deliberately useless)

Part 1 — static RSA decryptable with the private key · portal_tls.pcap + server.key

1 · Identify the cipher suite 🟢 Easy

Open portal_tls.pcap in Wireshark. Which cipher suite did the server pick, and what key exchange does it imply? Why does that decide whether the private key can decrypt anything?

💡 Wireshark steps 
Display filter:  tls.handshake.type == 2          # Server Hello
Packet Details ▸ Transport Layer Security ▸ Handshake Protocol: Server Hello ▸ Cipher Suite
→ TLS_RSA_WITH_AES_128_CBC_SHA256 (0x003c)
  TLS_RSA_*  =  static RSA key exchange, NO forward secrecy
  The client encrypts the pre-master secret with the server's PUBLIC key,
  so the matching PRIVATE key recovers it → session keys → full plaintext.

2 · Decrypt with the private key — request, login, flag 🟡 Medium

Add server.key and read the plaintext. What HTTP request was made? Which credentials were sent? What flag (and what other secret) is in the response?

💡 Wireshark steps 
Edit ▸ Preferences ▸ Protocols ▸ TLS ▸ RSA keys list ▸ Edit… ▸ +
   Key File = server.key        (IP Address / Port / Protocol: leave blank, or Protocol = http)
   OK ▸ OK   → the "Application Data" rows now decode as HTTP
Right-click any packet of the session ▸ Follow ▸ TLS Stream   → plaintext request + response
✅ what you should see 
GET /portal.html HTTP/1.0
Host: portal.lab.local
Authorization: Basic YWRtaW46QXV0dW1uIzIwMjU=      → admin : Autumn#2025
Cookie: SESSIONID=9f2c1a7b4e; role=admin

Response body:  FLAG{tls_rsa_no_pfs_is_decryptable}
Bonus leak:     Server=db01;Uid=svc_portal;Pwd=Autumn#2025;   (DB connection string)

Decode the Basic header: Packet Details ▸ Hypertext Transfer Protocol ▸ Authorization ▸ Credentials
(Wireshark decodes it for you), or Analyze ▸ Follow ▸ TLS Stream and read it in the clear.

Part 2 — ECDHE / forward secrecy the key is useless · portal_pfs.pcap + portal_pfs.keys

3 · Identify — and watch the private key fail 🟠 Hard

Open portal_pfs.pcap. Same portal, same server.key. Read the cipher suite, then add the key exactly as in Part 1 and explain why nothing decrypts this time.

💡 Wireshark steps 
Display filter:  tls.handshake.type == 2          # Server Hello
Server Hello ▸ Cipher Suite
→ TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 (0xc02f)
  ECDHE  =  ephemeral elliptic-curve Diffie-Hellman  →  FORWARD SECRECY
  RSA here only SIGNS the handshake (authentication); it does not carry the secret.

Now try the Part-1 trick:
Edit ▸ Preferences ▸ Protocols ▸ TLS ▸ RSA keys list ▸ + ▸ Key File = server.key
→ Application Data stays "Encrypted Application Data"; Follow ▸ TLS Stream shows only garbage.
  The session keys come from an ephemeral DH exchange that never travels on the wire,
  so the RSA private key cannot reconstruct them.

4 · Decrypt the right way — TLS key log 🔴 Expert

Use the client-side key log portal_pfs.keys (an SSLKEYLOGFILE captured at handshake time) instead. Report the request, the credentials and the flag.

💡 Wireshark steps 
Edit ▸ Preferences ▸ Protocols ▸ TLS ▸ (Pre)-Master-Secret log filename ▸ Browse… ▸ portal_pfs.keys ▸ OK
Right-click a packet of the session ▸ Follow ▸ TLS Stream   → plaintext

How you get such a file for real: run the CLIENT with the env var set, e.g.
  SSLKEYLOGFILE=keys.log curl https://portal.lab.local/   (same variable works for Firefox and Chrome)
✅ what you should see 
GET /portal.html HTTP/1.1
Authorization: Basic YWRtaW46V2ludGVyIzIwMjY=      → admin : Winter#2026
Cookie: SESSIONID=aa11bb22; role=admin

Response body:  FLAG{ecdhe_pfs_needs_the_sslkeylogfile}
Bonus leak:     Server=db02;Uid=svc_portal;Pwd=…   (DB connection string)
Lesson: a leaked server key decrypts every past static-RSA session ever captured (Part 1) but nothing that is forward-secret (Part 2). ECDHE is why — to decrypt forward-secret TLS you need key material from an endpoint at capture time (SSLKEYLOGFILE), not the server's private key. This is why modern TLS is ECDHE-only, and why a key log — not the private key — is how you decrypt your own traffic for debugging.
