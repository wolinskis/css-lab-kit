1 · Is this legit? Header & authentication analysis 🟢 Easy

Read the headers only. Does the message pass SPF / DKIM / DMARC? Compare the From: domain with the recipient's real domain (vulncorp.local). Verdict?

💡 starter command 
grep -iE '^(from|authentication-results|dkim|received):' phishing.eml
head -n 14 phishing.eml          # the whole header block, nothing else

What you should see: spf=fail, dkim=none, dmarc=fail — every sender check fails. From: is it-support@vulncorp-secure.com, a look-alike of vulncorp.local. Verdict: phishing.

2 · Where does it really go / come from? 🟡 Medium

Three questions: where do replies land, where does the "Reverify" link really point, and which IP handed the message to our mail server (the first external hop in the Received chain)?

💡 starter command 
grep -i '^reply-to:' phishing.eml
grep -oE 'href="[^"]+"' phishing.eml
grep -i '^received:' phishing.eml          # read bottom-up: the LAST one is the origin hop
grep -oE '\[[0-9.]+\]' phishing.eml

What you should see: Reply-To: <credentials@evil-collector.ru> (replies go to the attacker, not to the From). Link = http://vulncorp-secure.com.evil-collector.ru/login — the registrable domain is evil-collector.ru; vulncorp-secure.com is just a sub-label to fool the eye. Origin IP = 185.165.240.54 (external, reverse DNS "unknown").

3 · Don't trust the MIME tree 🟠 Hard

Map the MIME structure: how many parts, what are they, and what does the attachment really contain? Then look past the closing boundary — is the file really finished where the message ends?

💡 starter command 
grep -n -- '--===============LABKIT==' phishing.eml           # 2 openers + 1 closer (ends in --)
grep -n -iE '^content-(type|disposition)' phishing.eml
grep -A1 '^Content-Disposition' phishing.eml | tail -1 | base64 -d ; echo     # the "invoice"
sed -n '/^--===============LABKIT==--/,$p' phishing.eml              # everything AFTER the closing boundary
strings -n 20 phishing.eml | tail -8

What you should see: multipart/mixed with an HTML part and a PDF attachment invoice.pdf that decodes to %PDF-1.4 decoy invoice - nothing useful here — a red herring. After --===============LABKIT==-- there is a fake X-Note: archival blob below (not part of the message) header followed by a long base64 run. A MIME parser / mail client stops at the closing boundary and never renders it — only the raw bytes show it.

4 · Recover the hidden key 🔴 Expert

Prove what the appended blob is, locate it by byte offset, carve it out and decode it. No flag — recovering the key is the objective.

💡 starter command 
echo -n '-----BEGIN OPENSSH' | base64        # -> LS0tLS1CRUdJTiBPUEVOU1NI  (what to grep for)
grep -aboF 'LS0tLS1CRUdJTiBPUEVOU1NI' phishing.eml   # -> 1506:LS0tLS1CRUdJTiBPUEVOU1NI  (0-based byte offset)
tail -c +1507 phishing.eml | base64 -d            # tail -c +N is 1-based: offset+1
# or, boundary-driven instead of offset-driven:
sed -n '/^--===============LABKIT==--/,$p' phishing.eml | grep -v -e '^--' -e '^X-Note' | base64 -d

What you should see: a -----BEGIN OPENSSH PRIVATE KEY----- … -----END OPENSSH PRIVATE KEY----- block (a training placeholder key). Lesson: data appended outside the MIME tree is invisible to parsers and mail clients — always grep / strings the raw bytes, never trust the rendered view. Triage order for a hidden artifact in an email: boundaries → raw bytes → headers; steganography and PDF internals are last resorts, not first.

⚠️ Intentionally vulnerable — training only. Synthetic headers, fake domains and IPs, placeholder key; the "private key" is not a real credential. Never use in production.
